# Package signin (E2): sign-in hygiene, and preference sync that holds

After that it signs out here anyway, offline too, and says "Signed out here. Your other devices stay signed in." A quiet "Sign out everywhere" link in the signed-in card opens the CX confirm sheet. ## Decisions

- CTO call: the local sign-out waits five seconds for the server at most (`LOCAL_SIGN_OUT_WAIT_MS`), then finishes here. A late answer only ends this device's server session, which is what was wanted. "Sign out everywhere" has no such cut-off: a request that landed after a give-up would sign everything out after the person was told nothing changed.
- CTO call: the local sign-out refreshes through `freshSession` directly, not the store's `freshAuth`. On a dead token, `freshAuth` runs the expiry path (keeps team drafts, and shows the expiry toast) before the sign-out's own `forgetSession`. "Sign out everywhere" does use `freshAuth`: if the sign-in has already expired, the expiry line it shows is the honest one, and the failure copy ("still signed in everywhere") would be false.
- CX call: a local sign-out whose server call failed still shows only CX's toast. The build doc asked for a surfaced failure, but CX ruling 4 says the sign-out always completes, and the person can do nothing with a failure line here.
- CX call: after "Sign out everywhere" works, the toast reads "Signed out everywhere. Your other devices sign out within an hour." CX gave no success copy, so this repeats the confirm's own promise.
- CX call: the confirm follows the app's confirm grammar (`ForgetCurrentConfirm.tsx`): Cancel as a ghost button first, then "Sign out everywhere" in danger style.
- "Sign out everywhere" also asks first when team vault text is unsent (the same sheet as Sign out, with `unsentFor`), because it deletes that text the same way.
- CTO call: `freshSession` also remembers the last token it spent and the session that replaced it (cleared by any `clearSession`). Re-reading the sealed store alone leaves a window: a read issued before the flight's save lands after the flight ends and returns the spent token. The existing APP-1 test, which keeps its session only in memory, depends on this too.
- CTO call: a refresh only writes or clears the stored session when that session belongs to the same person, and only if no clear happened while it was out. Otherwise a slow refresh during a sign-out would sign the device back in on the next launch, or overwrite the next person's sign-in.
- A remote entry more than five minutes ahead is ignored, not erased. It never overrides a value on this device and is never applied here. When this device has no value for that key, the account's entry is written back unchanged, so a device with a fast clock loses nothing it set.
- `prefsUpdatedAt` stays as a legacy read, used as the stamp of any key without its own. The first v2 sync writes every key's stamp and clears it. An unstamped value loses to any account value (a new phone takes the account's) and is added, stamped now, when the account lacks that key. This matches v1's "an account with none takes the device's".
- A device from before this build has no `prefsOwner`. Its first sync records it and keeps its stamps, because there is no way to know whose they were. `forgetSession` records the leaving user, so the rule holds from then on.
- A sync that sees a local change land while the account's copy was being read stops without writing. That change's own push merges again 1.5 s later.
- Egress: the `preferences` entry is unchanged. The same preferences go to the same place at the same moments. Each push now reads the account's copy before it writes, and nothing new leaves the device.
- Outside the named test files, `app/test/privacyCalls.test.ts` needed a change. It fed the ethics upload through a mocked `authSession`, and now it hands a session in with `setEthicsAuth`.

## What remains

- Preferences on `user_metadata` have no compare-and-swap. Two devices whose syncs overlap within one read and write (about 100 ms) can still drop one key. Per-key merging narrows the loss from "any change within the debounce window" to that overlap. A server-side merge (an RPC or a per-key table) would close it. See `app/src/state/signinOps.ts` (`createPrefsSync`).
- An older build reads a `v: 2` record as unknown and pushes its own `v: 1` record at launch. This build merges it back by that record's one time, so mixed fleets converge but write more often (`app/src/lib/settingsReach.ts` `readPreferencesRecord`).
- `app/src/screens/SettingsScreen.tsx:1053` still calls `syncNoticePrefs` after `saveSettings`, which now does it too. The extra call is harmless. It was left alone because removing it also changes that file's import line, and other packages are editing that file.
- `app/src/lib/reviews.ts:38` and `app/src/lib/abuseReview.ts:21` refresh the store's session object through `freshSession` directly, so the store's memory never learns the new token. The re-read and the spent-token memory make this safe now. Routing them through the store (as ethics now is) would be cleaner.
- "Sign out everywhere" closes its sheet on tap and reports by toast. While the global call is out, the card still shows signed in, with no busy state.
- Device check (Mac and iPhone on one account): sign out on the Mac. The phone stays signed in now and an hour later.
- Device check: tap "Sign out everywhere" on the phone. The phone signs out at once, and the Mac within an hour, with "Your sign-in expired. Sign in again."
- Device check: turn on airplane mode and tap Sign out. It finishes at once with "Signed out here. Your other devices stay signed in.", and a relaunch stays signed out.
- Device check: within one minute, change the theme on the Mac and the effort on the phone. After both relaunch, both devices show both changes.
- Device check (two iPhones, or an iPhone and an iPad, on one account; the switch shows only on a phone): turn Downloads notices off on one. Relaunch the other and let a download finish there in the background. No notice should arrive.
