# Build 2026-09-29, package D1 "release": release integrity for every desktop update

## Log

Every desktop update is now checked before it runs, per CTO rulings 1 and 2. One `verifyAsset` (`app/electron/releaseVerify.ts`) checks a detached Ed25519 signature through `node:crypto` over exactly `openshore-release-v1\n<asset name>\n<sha256 hex>` against a key pinned in `app/electron/releaseKeys.ts`. There are two keys, `MAC_RELEASE_PUBLIC_KEY` and `DESKTOP_RELEASE_PUBLIC_KEY`, and both start empty. The asset name must carry the target version as a whole number, so an older signed build cannot be served as the new one: its name gives the old version, and renaming it breaks the signature. On the Mac (`macUpdate.ts`, `updateMacInPlace`), a missing key, a missing or unreachable `.sig`, or a bad signature opens the release page before `hdiutil attach` or `ditto -x`. With no key or no `.sig`, nothing downloads at all. Quarantine is cleared only on a verified bundle. The swap script keeps `<bundle>.old` until the new version writes its version into `userData/launched-version` (`writeLaunchMarker`, called at ready on macOS). If no marker appears after 120 s, the script stops a hung new app, restores `.old`, and opens it. On Windows and Linux, `installIfVerified` runs on electron-updater's `downloadedFile` before `quitAndInstall`, fetching `<name>.sig` from the same release. While no desktop key is pinned it skips the check and logs that it did. `app/scripts/release-keygen.mjs` prints both key pairs with plain instructions. `app/scripts/release-sign.mjs` signs files from a key held in a named environment variable. Codemagic's `mac-desktop` job signs after packaging with `OPENSHORE_MAC_SIGNING_KEY` from its own group, `openshore-mac-signing`, and uploads the `.sig` files. `mac-release.sh` does the same when the variable is set. `release.yml` now has top-level `contents: read`. Only `publish` gets `contents: write`, and it runs in the `release` environment, where it signs every `.exe`, `.AppImage` and `.deb` with `OPENSHORE_DESKTOP_SIGNING_KEY`. When that secret is absent, the release still publishes unsigned. The Windows certificate stays optional, and the publisher name is set only in the signed branch. Ollama's Windows installer now carries the Mark of the Web. `docs/release-signing.md` gives the founder's one-time steps, and `docs/MAC-DESKTOP.md` describes the new Mac behavior. Tests added: `app/test/releaseVerify.test.ts` (30) and `app/test/macUpdate.test.ts` (17). Both run the real signing script. The swap script runs under `/bin/sh` against stand-in bundles, and a source guard covers every download-then-run path. On the old tree, 26 of the 47 fail. Gates are green. Engine: 126 files, 1949 passed and 1 skipped. App: 198 files, 2694 passed and 2 skipped. Both typechecks, lint, Prettier and the app build pass as well. Egress: no new host, because the `.sig` files come from github.com, which is already listed under `updates`.

## Decisions

- Two keys, one per build service, following the ruling's two secrets. A leak on Codemagic cannot sign Windows or Linux updates, and a leak on GitHub cannot sign Mac updates.
- Key format: the public key is the base64 of its 32 raw bytes, so it can be pasted into a constant. The private key is base64 PKCS#8. The app imports the public key as SPKI DER built from a fixed prefix, which is the most portable path under Electron's BoringSSL.
- A version matches only as a whole number, so `0.1.5` does not match `0.1.50`, `10.1.5` or `0.1.5.1`. The signing script refuses a file that the app would refuse: the wrong version, or a name GitHub would rename.
- Mac: refusals before the download (no key, no `.sig` asset, or a `.sig` that cannot be fetched) open the release page and leave the bar as it was. A refusal after the download sets the bar to failed and opens the page. The `.sig` is fetched first, so a refusal costs no large download.
- Windows and Linux: a refusal is an updater error, so the bar reads "did not finish" with Try again. It does not open the release page, because a tampered release would serve the same file there. The check runs just before `quitAndInstall`, as ruled, not at download time.
- The launch marker holds the version, and the script clears it before opening the new app. A stale marker cannot pass for the new version. Tools are named by absolute path, and every path is single-quoted.
- CTO call: `nsis.artifactName` is now `${productName}-Setup-${version}.${ext}`. The live release v0.1.45 stores `OpenShore.Setup.0.1.45.exe`, because GitHub turns spaces into dots, while its `latest.yml` points at `OpenShore-Setup-0.1.45.exe`. So Windows in-place updates were already failing on a missing file. The signature covers the name, so the name the app downloads must be the name that was signed.
- electron-builder 26 has no `win.publisherName`. The setting now lives at `win.signtoolOptions.publisherName` and defaults to the certificate's common name, which is written into `app-update.yml` only on a signed build. The workflow therefore sets it by the certificate's presence: there is a signed branch and an unsigned branch (`env -u`), with the comment that every later build must be signed. `package.json` holds no static value.
- CTO call: Ollama's Windows installer gets a `Zone.Identifier` stream (zone 3), so the listed reason, SmartScreen, is true. Without the mark, SmartScreen never looks.
- The publish job checks out only the signing script, with `persist-credentials: false`, and uses the runner's own Node. No install runs in the job that can write.
- `DOWNLOAD_THEN_RUN` lives beside `verifyAsset`. The guard defines a download as a fetch streamed to disk, or electron-updater's `downloadUpdate`.
- `mac-release.sh` signs when `OPENSHORE_MAC_SIGNING_KEY` is set. Otherwise Macs with the key would refuse every Mac build made by hand.

## What remains

- Founder, once (`docs/release-signing.md`): run the keygen, add `OPENSHORE_MAC_SIGNING_KEY` to the Codemagic group `openshore-mac-signing`, create the `release` environment limited to `main` and `v*` with no reviewer, add `OPENSHORE_DESKTOP_SIGNING_KEY` to it, paste both public keys into `app/electron/releaseKeys.ts`, and push. Until then, a Mac running this build opens the release page instead of updating in place. That is a visible change, and it is the ruled one.
- Codemagic: confirm that the first Mac build after merge runs with the group listed before it exists (`codemagic.yaml:236`). If it fails, create the group first.
- Device checks. Ed25519 verification inside the packaged Electron on macOS, Windows and Linux (the tests run on Node). A signed Mac update end to end: the new version opens, and `.old` is gone within seconds. A Mac update whose new bundle cannot start (remove its executable): after two minutes the old app is back and open. A Windows update with the key pinned installs, and one with a changed `.sig` shows "did not finish". AppImage and deb updates behave the same way. The first Windows release after the rename lets a pre-rename install update in place. The Ollama installer on Windows shows SmartScreen's check on NTFS.
- `app/src/components/UpdateBanner.tsx:31` does not show `detail`, so a refused signature reads only "did not finish". CX should decide the copy for a refusal.
- A Mac the watchdog restored offers the same update again (`app/electron/main.ts`, `checkMacUpdate`), because nothing remembers a rolled-back version.
- electron-updater keeps a refused download in its cache. The next try downloads it again (or reuses it) and refuses it again, so it is harmless, but it is not cleaned up.
- `app/electron/macUpdate.ts`, `updateMacInPlace`, leaves its work folder behind when a tool fails after the check. This was already true before this package.
- The guard's download pattern (`app/test/releaseVerify.test.ts`, `savesDownload`) would miss a download written with `fs.writeFile` of a buffer. A new path of that shape needs to be listed by hand.
- Builds installed before this one have no check. Protection starts with the first build that carries a pinned key.
