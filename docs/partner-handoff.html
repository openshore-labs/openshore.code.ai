The product

What OpenShore is

OpenShore is a native app, one codebase running across the desktop (Linux, macOS, and Windows) and mobile (iPhone, iPad, and Android), that chats and builds software using a stack of models you choose, on hardware you own and keys you hold. It is shaped like a modern coding agent, the tool you already know, but the default engine is your local models rather than one vendor's cloud.

A note on names as you read the code: the product is OpenShore. The engine and this repository are called OS Code (the osc CLI, the os-code/ package), so you will see that name in the tree. Product is OpenShore, engine is OS Code.

The mission. Give local and self hosted models the complete, polished experience developers expect from the best cloud coding agents, and make the cloud a deliberate choice rather than the default. Your machine, your models, your keys. Nothing is rehosted or proxied, and no product analytics leave the device.

Who it is for. Developers and technical builders who want a capable coding agent without handing their code and prompts to a single provider by default. People who already run Ollama or llama.cpp, who hold their own API keys, and who care that spend and network access are visible and asked for.

The color language, here and in the app

Teal is local and private. The work runs on your own hardware, offline capable, no spend. This is the default posture.
Amber is cloud and spend. The work leaves your machine to a provider on your key. The app never routes here on its own, and money always asks first.

One model in your stack is the reasoning anchor, the quarterback. It frames the request, plans the work, and hands each part to the specialist best suited to it. Specialists plug into named categories: Coding, Writing, Analysis, Image reading, and Fast. Any category with no specialist placed, the quarterback runs itself.

The workflow

How a prompt actually runs

This is the single workflow the app is built around. Think of it the way a coach runs a play. My Stack is the anchor. The reasoning model frames the request, draws up a play, shows you a brief, and runs it, handing each step to the model that owns it.

A step's owner is a category, or a specific model: Coding Writing Analysis Image reading Fast

It works on the phone alone over My Stack. A step that must edit a repo or run commands runs on your paired computer's engine when you are docked, with the engine's real approvals surfaced in the chat. Cloud is used only if you placed a cloud model, and spend asks first. A weak anchor, an unreachable model, or a one step request all fall back to a plain routed answer, so a modest stack still just works.

The difference from a single cloud model A single model answers everything itself. Here the reasoning model is a router and a planner. It keeps the plan visible, sends each part to the model that is actually good at it, and can revise the rest of the plan when a result changes the picture. It is closer to running a small team than asking one expert.

The stages
  1. Setup.

    The chat connects to its repos and inherits their markdown instructions. My Stack for the current status, Offline, Offshore, or Docked, is loaded: the reasoning anchor plus its placed specialists.

  2. The harness.

    Every prompt flows through always on filters (ethics) plus curatable ones (skills, preset markdowns, the vault). Ethics can never be turned off. The rest you curate.

  3. Framing.

    The reasoning model reads and frames the prompt, asking a clarifying question only when a wrong assumption would waste real work. The clarify card renders tappable option chips, and a typed answer works too.

  4. The play.

    An ordered list of steps, each owned by a category or a specific model, with dependencies, so a coding step can feed a writing step that feeds a vision step. Any category with no specialist is run by the reasoning model.

  5. The brief.

    Before it runs you see the play as a short checklist, each step tagged with the model that will run it, updated live.

  6. Run and synthesize.

    Steps run in dependency order. At bounded checkpoints the reasoning model can re-plan the remaining steps. The final answer is composed by the reasoning model and streamed.

My Stack, the router, and BYOM

Built

Your stack is the roster of models the app draws from: one reasoning anchor plus specialists in named categories. You can bring your own cloud keys, or connect any OpenAI compatible endpoint you run yourself.

Open the engineering detail
Spec
  • The anchor plus categories. Categories are Coding, Writing, Analysis, Image reading, Fast, plus image generation, embedding, and a Custom slot for a specific model with a "when it is called" trigger.
  • Owner resolution. A step resolves to its placed specialist, or falls back to the reasoning anchor, or to a reachable capable model. Vision has a local slot and a cloud slot, preferring a capable local model when present.
  • Three connection statuses. Offline (local only), Offshore (your cloud keys), and Docked (paired to your computer). Each has its own stack, so the app knows what it can run right now.
  • Prefab stacks. One tap downloadable presets, auto derived from the live catalog and eval scores, not hand authored, so they reassess as models change.
  • Cloud connections. Bring your own key for Claude (Opus 5, Sonnet 5, Haiku 4.5), OpenAI (GPT-5, GPT-5 mini), Gemini (2.5 Pro, Flash), and Kimi (Moonshot). The app never routes to cloud on its own, and spend asks first.
  • BYOM. Connect any model you control at an OpenAI compatible endpoint, on your own server, treated as a first class stack member.

The Marketplace and model catalog

Built

A place to find and install models. It is a catalog, not a weight host: models download straight from their public sources, and OpenShore never rehosts weights or proxies inference.

Open the engineering detail
Spec
  • Direct from source. Downloads pull from Hugging Face and Ollama, with license flags shown honestly. Nothing is rehosted.
  • Browse by family, then size. Model families are derived on the client from the id and source ref, so today's feed and the bundled seed group the same way.
  • The phone storefront. One tap packs keyed to the connection status (Offline, Offshore, Docked), a "Runs on this iPhone" shelf, and a "Desktop and home servers" divider below which no control ever says Get on a phone.
  • Honest popularity, several axes. A benchmark "OpenShore fit" score, community stars (a separate signal, always shown with a count), your own most used (fully local), and staff picks. No axis is invented.
  • Live discovery. Trusted publishers only, both axes. A discovered model with no eval is labelled unrated rather than given a fake star.
  • The catalog builder. A CI job builds, gates, and publishes catalog.json to the marketing site daily, so the feed refreshes with no intervention.

On-device models, the engine, and pairing

Needs a device

The desktop is home. It runs the engine and a private daemon. The iPhone pairs to it over Tailscale and can also run pocket sized models fully on the phone. The phone is a remote control and a viewer, not the compute.

Open the engineering detail
Spec
  • Pocket inference. On iOS, GGUF models run through llama.cpp on Metal. On the desktop the on-device path runs through Ollama.
  • The two built in guides. Harbor Light (SmolLM2-135M, about 105 MB, bundled in the app, offline, a grounded guide not a reasoner) and Harbor (Qwen3-1.7B, about 1.1 GB, a real download, the first capable coding agent with web search).
  • Memory aware. The store is honest about the phone's memory limit, not storage, and a memory warning unloads the model so the next send reloads cleanly.
  • The daemon. Binds Tailscale or loopback, never 0.0.0.0, behind a bearer token. Shell is default deny with approvals.
  • Free desktop chat. A stateless /chat route builds only a provider and streams one completion, with none of the acting machinery, so chatting with your own local models is free. The coding agent stays behind Personal.
  • Terminal Control. A per machine switch. Off keeps the model out of the terminal entirely.

The coding agent, built to the Claude Code contract

Built

The chat with a desktop repo is built to work the way Claude Code works, so someone who knows one knows the other. Same permission modes, same transcript grammar, same approvals, enforced by the engine.

Open the engineering detail
Spec
  • Four permission modes, engine enforced. Default asks before every edit and command, Accept edits lets edits flow and asks for shell, Plan is read only and ends in a plan card, Bypass runs everything except cloud spend. Plan mode filters the tool specs to read and network at the engine, not the client.
  • The tool set. readFile, writeFile, editFile, glob, grep, searchRepo, runShell, readTerminal, git (gitStatus, gitDiff, gitLog, gitCommit), webSearch, webFetch, todoWrite, delegate to a specialist, image tools, and the vault and project memory tools.
  • One event protocol. Todos, plan proposals, mode, repo chip, and title are all DriverEvents, so the desktop and the phone render them from one reducer and the journal replays them losslessly.
  • The composer grammar. Slash commands, @ for repo files, # to save a line to the project's standing instructions, a queued message mid run, approvals that stack honestly with "always allow in this project" as an engine scoped rule.
  • Project memory. Notes live inside the project's primary repo in an "OpenShore Project [name] MDs/" folder, committed with the code, with a read only view in the app.
  • Project secrets. Reach the model only when the orchestrator is a local model, under an egress lockdown that never escalates to the cloud.

Repositories and the Vault

Built

A per repo storage seam (shipped as "Repositories") and a native Obsidian style knowledge base (the Vault) on top of it. Your notes are real markdown files you can open in Obsidian.

Open the engineering detail
Spec
  • The seam. Path and bytes shaped, with a single writer lease from day one, so the phone can browse and buffer through the outbox while the desktop shells out to real git.
  • Storage providers. Local, iCloud Drive (a native Capacitor plugin over the app's ubiquity container), and Google Drive (OAuth PKCE, drive.file scope only to avoid a CASA assessment). Readiness is a runtime probe, never a hardcoded flag.
  • Sealed secrets. Secrets on untrusted storage are sealed under a per repo key from the credential store, never the device key.
  • The Vault. Native markdown browsing, wikilinks worn in the local teal, and the honest compat claim: point Obsidian at the same folder and it just opens.
  • Agent writes. User directed or agent proposed with approval, never silent.
  • Ships as "Repositories." The gitOS codename stays internal, a Git trademark call.

My Crew and routines

Needs a device

A routine is a crew member, a task, a workspace, and a clock. When the clock strikes and your computer is on, the scheduler opens a headless journaled session on your own machine and leaves a dated note in the Vault. The copy is honest: "while your computer is on," never "always on."

Open the engineering detail
Spec
  • The safety contract. One run on the box at a time and one per routine. A slot the machine slept through is recorded as skipped once and never replayed. An unanswered approval times out to a denial after 15 minutes, never to an approval. A wall clock cap per routine (5 to 60 minutes).
  • Least privilege. Read only routines run in plan mode, edit routines in acceptEdits. A routine runs only in an admin provisioned workspace, with headless permission hardening so an allow default cannot make shell, push, or cloud spend silent.
  • Cross device control. You set up and control routines only while docked over Tailscale, and can always view. Three header states: In control, View only, Not set up. Away from home the command center shows a cached snapshot and hides every control.
  • The command center. A live headline with four counts, a Waiting for you list, the roster with presence dots, and a results inbox that opens the rendered vault note with the transcript one tap away.
  • The advisor org. The founder's advisory team ships as a Crew preset, eight named members, all advisory, the person decides.
  • One preset. Morning review, weekdays at 06:00, read only, so its first unattended run can never need an approval.

The always-on ethics layer

Built

A safety filter wraps every model call, local and cloud alike, on both sides: the prompt is screened before a model sees it, and the answer before a person does. There is no setting, config key, or environment variable that turns it off, and a test fails the build if one ever appears.

Open the engineering detail
Spec
  • One chokepoint, installed by construction. The provider registry hands out only guarded providers, and the driver factory wraps every driver, so a new call site cannot forget the layer. There is no unguarded object to call.
  • Both sides, and fail closed. A stream screener releases text only after a clean screen, so a blocked answer is never partially shown. Any throw or timeout blocks, and is recorded as our fault, never counted toward enforcement.
  • The three tiers. Tier 1 is a hard block with no consent override (CSAM, non consensual intimate imagery, concrete CBRN uplift). Tier 2 gates recreating a real person's face or voice behind an authorization assertion. Tier 3 is protected: legal adult content, dark fiction, horror, satire, security research.
  • Provenance. Generated images carry a C2PA vocabulary record. It is unsigned and says so, because no signing certificate is held yet.
  • Enforcement is server side. The ladder computes from recorded events so a reinstall cannot reset it. There is no IP address anywhere in the product: no column, no header reading, no ban queue.
  • Framework alignment. A self attestation to NIST AI RMF, ISO/IEC 42001, and C2PA. No third party has certified it, and the repo says so plainly.

Premium by default: the build standards

Built

OpenShore is a machine that builds usable software, so the quality bar is enforced rather than hoped for. Two standards are injected into the models, and a third is pinned by tests on this repo's own screens.

Open the engineering detail
Spec
  • The UX standard. The twenty laws of UX plus a house motion and honesty bar, injected into the coding agent's system prompt as build instructions. On by default, off via a project's config or "skip the UX standard" in the chat.
  • The Humanizer. Anti AI writing tells, distilled from a dated Wikipedia snapshot treated as data, injected into the writing agent so output reads like a careful human wrote it. Surfaced as a "Humanize Writing" setting, on by default.
  • Motion and polish. One motion vocabulary of tokens, every tappable acknowledges the touch, everything that animates in animates out, transform and opacity never layout, native haptics, reduced motion always honored. Enforced by polish-standards.test.ts, which fails CI on drift.
  • Stack Health. A usage and sustainability dashboard, kept in the teal and water palette (local means private), with estimates labelled as estimates and a daily refresh cadence.
  • No em dash, anywhere. A repo wide guard forbids em dashes in all tracked source, comments included. This document is written under the same rule.

Voice mode and media attachments

Needs a device

A spoken conversation over the chat that is native so it works offline, and attachments that let a model reason over a video by its frames.

Open the engineering detail
Spec
  • Voice, native and offline. Listening reuses on device speech recognition with a silence based finalize; speaking is on device synthesis (Web Speech on desktop). You pick from the device's installed system voices, which keeps it clear of the Tier 2 voice likeness gate.
  • Natural breaks. Clarifying questions and plan approval are answered by voice; a tool or spend approval closes voice, shows the card, then voice reopens once it clears. Everything spoken lands in the transcript as text.
  • Video attachments. A model never receives a video. A clip is sampled into up to 12 downscaled frames tagged with order and timestamp, and those ride to a vision model as image blocks, so it can say plainly it reviewed the clip frame by frame.
  • Vision routing. Image reading is a placeable Stack category with a local slot and a cloud slot, each with its own effort.

Tiers and billing

Built, gates off for beta

Personal is an Apple only subscription. Commercial team plans run on Stripe. For the beta every pay gate is off behind one reversible switch, so the whole product is free to exercise while it is being built.

Open the engineering detail
Spec
  • Personal is Apple only. A 20 dollar a year auto renewable subscription bought in app on iPhone or iPad. There is no Stripe purchase for Personal; web and desktop point to buy on iPhone, then refresh the shared entitlement row.
  • Commercial on Stripe. Team plans use Stripe, since Apple forbids seat based SaaS in app. Seat ceilings are enforced in Postgres by security definer triggers.
  • Beta switch. One reversible flag, PAY_GATES_ENABLED=false, short circuits every gate to unlocked from one place. The Apple purchase and entitlement plumbing stays built underneath.
  • The edge functions. Stripe checkout, webhook, and portal; Apple notifications and purchase linking; push register, grant, and send; and the repo OAuth exchange. All in supabase/functions/.

Honest about the state

What is still rough

The founder tracks every open item in os-code/PROGRESS.md under "What remains." Here it is grouped the way it matters for you: what needs a real device to prove, what needs the founder to finish a configuration step, and what was deferred on purpose. None of it is blocking the beta.

Needs a device to verify

Built and unit tested, but the native path only runs on real hardware.

  • Voice mode on an iPhone (the decision logic is tested, the speech path is device only).
  • Video attachments on device and on a desktop with FFmpeg.
  • The phone storefront packs and shelves on a real phone.
  • On device memory path, a 4B loading and sustaining a reply without a jetsam kill.
  • Crew routines firing on the founder's machine, and the approval push arriving with the app closed.
Needs founder config

Code is ready; a credential or an account setting is the gate.

  • Apple secrets for the subscription and server notifications.
  • Google OAuth client ids before Drive can connect.
  • iOS memory entitlements on the App ID before the next distribution build.
  • The license choice. A "no license granted" placeholder stands until the founder signs one (the CFO recommends BSL 1.1).
Deliberately deferred

Chosen not to build yet, with a reason on record.

  • The org Vault tier, a real multi writer backend.
  • BYOM on device streaming (buffer then dump today).
  • Per seat Stripe billing (flat per band today).
  • The CLI and TUI (osc) is parked; the native apps are the product.
  • A ComfyUI image path and a tree-sitter code map, behind existing seams.
  • Two unconfirmed edges: a Linux safeStorage repro and a Codemagic access gate case.
For your first hour

Where to start poking

Everything needs Node 22 or newer and pnpm. The desktop runs the whole engine in process, so you can be chatting against a local model in a few minutes.

# clone your working branch, then from the repo root
corepack enable
pnpm install
pnpm desktop            # launches the desktop app on this OS (Linux, macOS, or Windows)

# checks across the workspace
pnpm -r build && pnpm -r typecheck && pnpm -r lint && pnpm -r test

Point it at Ollama (or any OpenAI compatible local server), grab a model in the marketplace, pick your quarterback, and chat. Desktop installers build with package:linux, package:mac, or package:win. The iPhone and iPad builds ship through TestFlight; see docs/TESTFLIGHT.md.
